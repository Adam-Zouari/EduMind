## Role

`edumind.extraction` converts a local image, PDF, DOCX, audio file, or video into an
`ExtractedDocument`. Production and experiments share the same contracts and
canonical results. Provisional extractors live in `src`; alternative adapters
remain beside their experiments until a benchmark-backed promotion.

```text
local path -> source detection -> extractor registry -> canonical document
           -> optional runtime cleanup -> revisioned cache
```

## Output contract

An `ExtractedDocument` contains:

- text and exact half-open character offsets;
- pages, timestamps, and bounding boxes where the source/parser provides them;
- structured heading, list, table, formula, caption, audio, and visual-text
  segments;
- source path, checksum, MIME type, parser profile/revision, warnings, and timing.

Tables and formulas are document elements, not separate source kinds. The original
parser representation is retained in metadata when it contains richer structure
than the text view.

`ExtractionRequest` freezes source identity and options. `ExtractionProfile`
freezes every behavior-changing choice: engine revision, device, OCR/table/formula
settings, routing, preprocessing, and normalization. The cache identity includes
the profile fingerprint, resolved request options, source checksum, source kind,
and MIME type, plus the complete verified model-bundle identity. Runtime verifies
the requested model bytes before cache lookup, including both video components;
changing a verified bundle invalidates the cache even at the same path/revision.
The cache schema is now version 2; old entries are misses, not silently relabelled
results. Renaming identical input reuses the extraction while returning the
current source name and path. Document metadata retains the resolved bundle
identities and their lock records.

Production may request an optional cleanup profile. Extraction benchmarks request
`normalization=none`, preserve candidate output, and use only the fixed prose
scoring [projection](../benchmarks/metrics.md#prose-scoring-projection) applied
identically to the reference and prediction. It compares text but does not
clean stored output. Structured output canonicalization is a separate operation
used only to make equivalent serialized objects stable for comparison, hashing,
and caching.

Document benchmark attempts bypass the completed-source result cache so each
measured request actually executes extraction. Loaded model/runtime reuse is
expected. Only the first measured output supplies quality scores; later outputs
are validated and retained for repeatability and timing. The
[document methodology](../benchmarks/extraction/document/methodology.md)
defines the benchmark lifecycle separately from production caching.

## Current production routes

| Source | Provisional route |
|---|---|
| Image | Docling Standard, RapidOCR, full-page OCR, TableFormer fast, formulas off |
| PDF | Docling Standard, RapidOCR, PDF-aware OCR regions, TableFormer fast, formulas off |
| DOCX | Native Docling ingestion |
| Audio | Pinned Whisper `small.en` on CPU |
| Video | FFmpeg media extraction with frozen Whisper and Docling visual-parser profiles |

Temporary video/audio/frame files are always cleaned. Optional backends and model
weights load lazily; importing the package has no download or filesystem side
effect.

Whisper requires a native object with string transcript text. Malformed chunks
or boundaries produce recoverable diagnostics. When chunk words do not cover the
native transcript, production retains that entire transcript without inventing
timestamps and keeps the parsed native chunks separately for inspection. Valid
missing boundaries, including an untimed tail, remain allowed; explicit silence
is distinct from a malformed response.

Video composition retains complete frame documents until assembly, rather than
flattening them immediately to text. Audio and visual segments retain modality,
native kinds, structured content, local offsets/IDs, and document provenance.
Frame-local IDs are namespaced, final offsets are rebuilt against the composed
text, and warnings retain frame/time context and remapped segment indices.

## Model preparation and failure behavior

Runtime model locations come from
`data/benchmarks/models/selected.json`, generated by the explicit steps in the
[installation guide](../setup/installation.md#3-model-storage-and-immutable-lock).

Missing paths or inconsistent revisions fail with the preparation command rather
than fetching a moving model revision. Recoverable extraction issues are returned
as structured warnings; backend failures retain internal detail without exposing
raw exceptions through the UI.
